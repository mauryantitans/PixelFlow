# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PixelFlow is a visual image-processing pipeline builder: a React/TypeScript frontend and a FastAPI/Python backend. Users build pipelines from **77** built-in OpenCV / scikit-image / PIL operations plus a user-editable **Custom Kernel** (78 in the palette), save pipelines as reusable **custom filters**, and run them in **Live mode** (single image, real-time incremental preview) or **Batch mode** (many images, as a background job on the server). The operation library is **schema-driven**: the backend registry is the single source of truth and the UI renders each operation's controls dynamically, including interactive inputs (click a point, drag a region, pick a color) and a kernel matrix editor. Backed by PostgreSQL in production, SQLite in local dev; image bytes in the database by default or in optional S3-compatible object storage.

## Architecture

### The operation registry — the single source of truth (most important contract)
Operations are declared **once, in the backend**, in the `backend/app/processing/` package. There are **no frontend operation config files** — the frontend renders entirely from the schema served by the API.

- `processing/param_specs.py` — the `ParamSpec` types: `int`, `float`, `odd_kernel`, `angle`, `enum`, `bool`, `color`, image-coordinate `point` / `points` / `rect`, and `matrix` (square odd-sized kernel with `presets`), `text` (short string), `steps` (an embedded list of `{name, params, enabled}`, max 30). Each spec knows its constraints, `.coerce()` (validate+normalize a raw value), `.schema()` (the DTO sent to the UI), and (for coords) `.to_pixels()`.
- `processing/registry.py` — `OperationSpec` (stable snake_case `id`, `label`, `category`/`subcategory`, `description`, ordered `params`, the `fn` callable, `aliases` = legacy display names, and `hidden` = runnable but not listed in the palette or the legacy count) and the `OperationRegistry` singleton. `ensure_registered()` lazily imports the operation modules. **`id` is the stable identity; never reuse/rename an id, and never remove an alias** — saved pipelines (`SavedPipeline.pipeline_data`) reference operations by display-name string and resolve through the alias map with zero migration.
- `processing/coords.py` — the ONE place for coordinate↔pixel mapping (normalized [0..1] → pixels), odd-kernel enforcement, and color parsing.
- `processing/executor.py` — `execute_step(image, step)`: skip if `enabled is False` (image passes through, no error) → resolve id/alias → validate+coerce params → map normalized coords against the *current* image size → run the callable. Returns a structured `StepError` per step instead of a silent no-op; one bad step never 500s the batch.
- `processing/preview_cache.py` — per-session LRU of intermediate images keyed by cumulative prefix hashes of `{name, params, enabled}` (powers incremental live preview; toggling a step off invalidates from that step on).
- `processing/operations/` — the actual functions, registered declaratively: `_builtins.py` (the original ~53 ops), `interactive.py` (Flood Fill, Crop, Inpaint Region — point/ROI/color), `extras.py` and `extras2.py` (the +22 stylize/photo/segmentation/morphology batches), `custom.py` (**Custom Kernel**: `cv2.filter2D` with a `MatrixParam` + presets, normalize/absolute/offset; **Custom Filter** (`custom_filter`, `hidden=True`): runs its `steps` param through `execute_step` in order and refuses nested custom filters). Operation bodies are plain `fn(image, **params) -> PIL.Image`.

**Coordinates are normalized [0..1] everywhere** in transport/storage and converted to pixels once in `coords.py` at execution. This survives preview downscaling and upstream geometry changes (e.g. an upstream Resize auto-rescales a seed point/ROI for free).

**Custom filters** are ordinary `SavedPipeline` rows with `category = "Custom filter"`. Adding one puts a single `Custom Filter` step in the pipeline whose params hold `filter_name` and a **snapshot** of the steps; editing the saved filter later doesn't change pipelines that already use it.

To add an operation: write the function, register an `OperationSpec` with typed params, and import its module in `registry.ensure_registered()`. The UI needs **no changes**. See [guides/ADDING_OPERATIONS.md](guides/ADDING_OPERATIONS.md).

### Pipeline execution
Pipelines are ordered lists of `{name, params, enabled?}` steps. `ImageProcessor.apply_operation` delegates to `executor.execute_step`. `apply_pipeline_with_timing_from_image(image, pipeline, source_key=...)` runs steps sequentially through the executor, captures each intermediate, records per-step millisecond timing and per-step `StepError`s into a `ProcessingResult`, and uses the **prefix cache** to recompute only the steps from the first change onward (`cached_prefix_len` reports reuse). `source_key = "{session}|{image_id}"` is threaded from the processing routes.

**Batch runs are background jobs.** `POST /api/processing/jobs` stores a `ProcessingJob` row (the table *is* the queue; no Redis) and wakes `utils/job_worker.py`: one daemon thread per backend process claims queued jobs one at a time with a conditional `UPDATE … WHERE status='queued'`, processes each image, saves every step as a `ProcessedImage` (through `app.storage`), and commits progress after each image. The browser polls `GET /jobs/{id}` and fetches `/jobs/{id}/results/{i}`; `/cancel` stops before the next image. Jobs left `running` by a restart are re-queued at startup (start over); finished jobs are deleted by the cleanup job after a day. Max 100 images per job. Ownership: the account, or for guests the `session_id` query param (others get 404). `JOB_WORKER_ENABLED`, `JOB_POLL_SECONDS`. The synchronous `POST /api/processing/process` still exists for API clients.

### The `/operations` schema endpoint
`GET /api/processing/operations` returns the grouped schema (`version` "2", `categories[] → subcategories[] → operations[]` with typed `params` and `hidden`) plus a legacy flat `operations` list + `total_count` (78; hidden ops excluded) for backward compat. The frontend fetches it once at startup.

### Backend layout (`backend/app/`)
- `main.py` — app factory, lifespan (`init_monitoring()` at import; init db = migrations with connection retries; auto-create first admin; start/stop the DB cleanup scheduler and the job worker), middleware wiring (CORS is added **last** so it is outermost and 403/429 responses keep CORS headers), global exception handler.
- `processing/` — the operation engine (see above). `utils/image_processing.py` is now a thin `ImageProcessor` façade over the executor + prefix cache.
- `storage/` — where image bytes live. `base.py` (`ImageStore` interface, `DatabaseStore`), `s3.py` (`S3Store`, boto3; AWS S3, Cloudflare R2, MinIO), `images.py` (the only helpers routes use: `save_image_bytes`, `read_image_bytes`, `delete_image_objects`, `object_keys`; a `before_flush` hook removes the objects of ORM-deleted rows after commit, bulk `query.delete()` call sites pass `object_keys` explicitly). `STORAGE_BACKEND=database|s3` + `S3_*`; rows keep a `storage_key` and the thumbnail stays in the DB; the API always serves the bytes itself (no public URLs). An invalid storage config stops startup; tests use `moto`.
- `core/config.py` — central `Settings` (env-driven). **Fails fast** (`sys.exit(1)`) in production if `SECRET_KEY` is still the default, and on an invalid storage config. Rewrites Render/Heroku `postgres://` → `postgresql://`. `USE_SQLITE=True` switches `DATABASE_URL` to a local SQLite file. Also `EMAIL_*`/`SMTP_*`/`FRONTEND_URL`.
- `core/security_config.py` — constants for CORS origins, rate limits (incl. per-IP upload/processing limits), login lockout, session/token expiry, file-upload limits, password policy. `core/business_rules.py` — quota/retention **seed defaults only**; the live policy is read from the DB `SystemSettings` row (admin-editable). `core/migration_helpers.py` — idempotent Alembic helpers (above).
- `core/database.py` — SQLAlchemy engine, `SessionLocal`, `Base`, `get_db` dependency, `run_migrations`, `init_db` (retries with backoff, logs the unreachable host).
- `models/db_models.py` — all ORM tables (`User` incl. `email_verified` and `preferences` JSON, `RefreshToken`, `LoginAttempt`, `Session`, `UploadedImage`, `ProcessedImage` (both with `storage_key`), `SavedPipeline`, `SharedPipeline`, `ProcessingJob`, `ProcessingHistory` (unused), `APIKey` (unused), `SystemSettings`). `models/schemas.py` — Pydantic request/response models (incl. `PreferencesUpdate`). `models/__init__.py` — `PipelineStep` (`name`, `params` widened to allow nested list/dict for coord/matrix/steps params, `enabled: bool = True`) and `StepError`.
- `api/routes/` — `auth` (incl. `PUT /me/preferences`, forgot/reset password, verify/resend verification), `oauth` (Google), `pipelines` (incl. share-by-link: `GET/POST/DELETE /pipelines/{id}/share`, public `GET /pipelines/shared/{token}`; declared before `/{pipeline_id}`), `admin`, `images_db` (upload incl. `/upload-multiple`), `processing_db` (`load_image_from_db`, the `/operations` schema, live/sync-batch processing), `jobs` (background batch jobs, mounted at `/processing/jobs`), `client_errors` (`POST /api/client-errors`: browser error reports, length-capped, 10/min per IP, logged + forwarded to Sentry). - `middleware/` — `RateLimitMiddleware` (per client IP + path, in memory; `TRUSTED_PROXY_HOPS` picks the real client IP from `X-Forwarded-For` behind Render/Vercel; `/health` and `/api/health` are exempt), `SecurityHeadersMiddleware`, `CSRFMiddleware`.
- `utils/` — `auth.py` (JWT/bcrypt, cookies, hashed + rotated refresh tokens), `admin_pin.py` (server-side admin PIN: 15-min signed cookie, `require_admin_pin`, wrong-PIN lockout), `account_tokens.py` (signed single-use tokens: password reset 1 h, email verification 48 h), `email.py` (`EMAIL_BACKEND=console` logs the email incl. link; `smtp` sends; per-address 1/min throttle lives in `routes/auth.py`), `job_worker.py` (above), `monitoring.py` (optional Sentry via `SENTRY_DSN`, `send_default_pii=False`; `report_client_error`), `session_db.py` (session activity: sliding expiry, ownership, guest→user linking), `cleanup_scheduler.py` (runs `cleanup_service.run_full_cleanup` every 15 min), `cleanup_service.py` (also deletes finished jobs), `quota_manager.py`, `settings_manager.py` (DB settings + validation), `datetime_utils.py`, `init_admin.py`. `session_manager.py` is **deprecated/unused** (old filesystem storage).

### Sessions, cleanup and the connection indicator
Each browser has a session id (`SessionUtils`, localStorage). The server records **activity** on it (upload, opening the workspace, processing, creating a job): `session_db.create_or_update_session` creates the row on first upload, slides `expires_at` forward on activity (throttled to one write/min) and refuses a session owned by another user (upload → 409 `session_owned_by_another_user`; signed-out owner → 401 `sign_in_required`). Signing out switches to a fresh guest session; signing back in restores the account's session in that browser. "Active" in the admin panel = activity in the last 15 min. `cleanup_scheduler` runs `CleanupService.run_full_cleanup` every 15 min (honours the admin auto-cleanup switch; retention/lifetimes come from `SystemSettings`). The header's `ConnectionStatus` badge only pings `GET /api/health` (no DB, no session writes); `/images/heartbeat` is deprecated and never creates sessions.

### Auth (httpOnly cookies + CSRF)
JWT access + refresh tokens (`python-jose`, bcrypt via `passlib`) are delivered as **httpOnly cookies**, never in response bodies or `localStorage`:
- `set_auth_cookies`/`clear_auth_cookies` in `utils/auth.py` set `pf_access` (httpOnly, Path=/), `pf_refresh` (httpOnly, Path=/api/auth), and a non-httpOnly `pf_csrf`. `get_current_user`/`_optional` read the token from the `pf_access` cookie or, for non-browser clients, an `Authorization: Bearer` header.
- **CSRF**: `middleware/csrf.py` enforces a double-submit cookie — cookie-authenticated unsafe requests (POST/PUT/DELETE/PATCH under `/api`) must send `X-CSRF-Token` matching the `pf_csrf` cookie. Exempt: login/register/oauth (no session yet), forgot-password/reset-password/verify-email (act only through the address or the token in the body), `client-errors` (only adds a log line), and the session-id-keyed `heartbeat`/`cleanup-session` (reached via fetch/beacon). The frontend echoes the cookie via axios request interceptors (`services/api.ts`, `services/auth.ts`).
- `/auth/login` and the OAuth callback set the cookies and return only the user; `/auth/refresh` reads the refresh cookie, **rotates** it (DB-backed `RefreshToken`, hashed), and re-sets cookies; `/auth/logout` clears cookies and revokes refresh tokens. Tokens carry a random `jti` so they're always unique.
- **Token refresh**: the access cookie lasts 30 min and the browser stops sending it afterwards, and image/processing routes accept guests, so the frontend refreshes **proactively** (`services/tokenRefresh.ts`: before a request, if `pf_csrf` exists and the tokens are 20+ min old) with a 401 refresh-and-retry fallback on both axios clients. A rejected refresh fires `pixelflow:auth-expired` → signed out.
- **Password reset / email verification**: `/auth/forgot-password` always answers the same (no account enumeration; Google-only accounts get a "use Google" email) and emails a 1-hour single-use link to `FRONTEND_URL/reset-password`; `/auth/reset-password` sets the password, revokes all refresh tokens and clears the login lockout. Registration and email changes send a 48-hour verification link (`/auth/verify-email`, `/auth/resend-verification`); verification is a reminder (banner), not a gate.
- Cookie attributes are env-driven: `COOKIE_SECURE` (default on in prod), `COOKIE_SAMESITE` (default `lax`), `COOKIE_DOMAIN`. **In production the frontend must be same-origin with the API** (a Vercel rewrite proxies `/api/*` → the Render backend; set `REACT_APP_API_URL=/api`) so cookies are first-party — see `frontend/vercel.json` and `deployment/DEPLOYMENT_GUIDE.md`.

Optional Google OAuth (`authlib`) gated on `GOOGLE_CLIENT_ID`/`SECRET`. First admin is auto-created on startup from `ADMIN_EMAIL`/`ADMIN_PASSWORD` if no admin exists. The admin panel's user-data views are protected by an **admin PIN enforced server-side** (`utils/admin_pin.py`).

- Frontend env: `REACT_APP_API_URL` (`/api` in production, via the Vercel rewrite), `REACT_APP_GOOGLE_CLIENT_ID`, optional `REACT_APP_TOKEN_REFRESH_MINUTES` (default 20).

## Deployment
Frontend → Vercel, backend + PostgreSQL → Render (optionally Cloudflare R2 / S3 for image bytes). Config in `deployment/` (`render.yaml`, `vercel.json`) and root `render.yaml`. Dockerfiles exist in `backend/` and `frontend/` plus a root `docker-compose.yml`; the backend entrypoint just starts uvicorn (migrations run in the app). Do **not** put real credentials in docs — provision the first admin via `ADMIN_EMAIL`/`ADMIN_PASSWORD`.

## Commit authorship (maintainer's rule)
- **Bug fixes** (`fix:` / `fix(scope):` commits): author *and* committer are the maintainer, with no Claude trailer lines:
  `git -c user.name="Mourya Arnepalli" -c user.email="97488932+Mauryantitans@users.noreply.github.com" commit -m "fix(...): ..."`
- **Everything else** (features, docs, tests, chores, refactors): commit with the session's default identity (Claude) as usual.
- Keep a fix in its own commit so the split stays clean; don't mix a fix into a feature commit.
